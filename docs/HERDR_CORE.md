# herdr-core as a backend

The Herdr desktop app (`herdr-app`) runs its terminals and agents in **herdr-core** (`hc`), not in the classic `herdr server` the app has always talked to. A machine may run either or both. This note says how the app reaches herdr-core and how hc's model maps onto the app's screens. The code is in `core/src/main/kotlin/.../core/hc/`.

Built against `hc` 0.1.14 (`hc schema`: OpenRPC, protocol generation 1). Its answers, as a real `hc connect` gave them, are the test fixtures in `core/src/test/resources/hc/` (paths and names scrubbed).

## Reaching it

- **Detection** (`HcDetection`), per machine, after the SSH login and beside classic herdr's own: one shell probe finds the default session's socket the way hc does (`HC_SOCKET`, else what the running core wrote in `core.lock` in its state folder, else the runtime folder), and only when it exists checks that the session's core runs: on Linux the process holding the lock on `core.lock` (read from `/proc/locks`, without taking it), elsewhere any `herdr-core serve` (`pgrep`; the socket alone where there is no `pgrep`) and lists the `herdr-core` executables (a running core's own installed build first, then `~/.local/bin`, `PATH`, the usual install places, the login shell's `PATH` only when nothing else had one). An `hc` on its own isn't taken for it: herbstluftwm ships one too.
- **Other sessions** (`HcDetection`'s probe, Linux only): herdr-core runs one core per session (`HC_SESSION`), each with its state folder (`~/.local/state/herdr-core/<session>/core.lock`) and socket (`<runtime>/herdr-core/<session>.sock`). Shepherdr 3 runs its agents in the default session. The probe names every other session whose core holds its own `core.lock` (`session<TAB>name<TAB>socket<TAB>pid<TAB>exe`); a socket left behind, a holder's (`*.holder.*.sock`) or a name with other than letters, digits, `_` and `-` doesn't count. Elsewhere a core process can't be told from another session's, so off Linux only the default session is followed, as before. `connect` to another session sets `HC_SESSION` as well as `HC_SOCKET`, so even in the moment's race a core it starts would be that session's.
- **Only a running core counts.** `hc connect` starts a core when none listens on its socket, and the app mustn't start a runtime on a machine whose owner doesn't use it. So `connect` is pinned to the socket found (`HC_SOCKET`) and refuses when it's gone. Left: a core that stops in the moment between the probe and `connect` gets a new core, as does, off Linux, a crashed core's socket while another session's core runs. A core found missing is looked for again every minute (the desktop app started later), one that went (a restart, an hc update) after 3 s; with no core running that is one short shell (a `test` of the socket and, on Linux, a look at each session's `core.lock` in `/proc/locks`) and nothing more.
- **Transport** (`HcConnection`): one `<herdr-core> connect` exec channel per machine on the existing sshj connection, kept for the connection's life and closed with it. `hello {generation: 1, framed: true}` as one JSON line, then framed mode: `[channel u32 LE][kind u8][len u32 LE][payload]`. Channel 0 carries JSON-RPC calls side by side; the event subscription and each attached terminal get a channel of their own, credited back as the app reads, so the one channel carries everything.
- **Client** (`HcClient`): `list`, `get`, `read`, `send`, `keys`, `interrupt`, `subscribe` (snapshot, then events) and `attach` (raw terminal bytes, keys, resize). Errors come back as `HcException` with hc's stable `kind` (`not_found`, `blocked`, …).
- **In the app** (`HostSession`): a machine running both shows both. `HostState.herdrCore` holds herdr-core's version, the core's name and its terminals as a `SessionSnapshot`, next to classic herdr's `HostState.snapshot`, which doesn't change; `awaitHerdrCore()` gives the client. herdr-core is followed outside the classic session's own scope, so a herdr-core failure or hang never fails or holds up the classic session.
- **herdr-core alone**: where classic herdr is missing (not installed, its session not there or not running) but herdr-core runs, the session stays connected for herdr-core and is **online** while herdr-core answers; `HostState.classicMissing` says what classic herdr lacks (`HostState.classic` is false), and the status says it again while herdr-core is gone too. Classic herdr is looked for again every two minutes, as that status's retry would, and at once on Retry; once it answers, the session starts over with both. A dropped SSH link ends the session as usual (checked every 5 s).

## The model

hc itself has terminals only. The desktop app adds its spaces and tabs as labels on each terminal it shows: `herdr.space` and `herdr.tab` (ids) and `where` (`<space> / <tab>`, the names, which `hc ls` prints). That is from herdr-app's source (`src/window.rs`, `write_where` and its `terminal.label` calls); the desktop app isn't installed on the machine the fixtures come from, so their terminals were started with `hc run` and labelled the same way by hand, and their statuses are real 7501 reports (Claude Code's own for one, `printf` for the others). `HcMapping.snapshot` turns live terminals into the app's own `SessionSnapshot`, so the screens read herdr-core as they read classic herdr. Every id starts with `hc:` so both can sit side by side.

| herdr-core | The app | How |
| --- | --- | --- |
| A space (`herdr.space`, name from `where`) | Workspace | `hc:<space>`; numbered in the order its first terminal started |
| A tab (`herdr.tab`, name from `where`) | Tab | `hc:<space>/<tab>` |
| A terminal (`t7`, `rohan/t7` on a machine hc added) | Pane | `hc:t7`; `HcMapping.address` gives `t7` back for hc's calls |
| A helper an agent started (`parent`) | Pane in its parent's tab | as the desktop app places it |
| A terminal the app doesn't show (`hc run`) | Pane in **Other terminals** | one workspace per machine, after the spaces |
| A program that reports a status (OSC 7501), or a known agent before it reports | Agent | `agent` from 7501's `app` (`claude-code` → `claude`), else the program's name; a shell whose agent quit is a terminal again |
| Status `idle` `working` `done` `blocked` | Same status | the program's own word, nothing guessed from the screen |
| Status `error` | Blocked, labelled "error" | it needs the human too |
| `blocked` with `kind` question or auth | Blocked, labelled "question" or "needs sign-in" | permission keeps the plain label |
| 7501 `msg` (else `title`) | The agent's subtitle | "Showing current date and time" |
| Terminal title | `terminalTitle` | Claude Code's "Greeting reply" |
| `status_ms` (when the word changed) | `stateChangeSeq` | alerts, notice ids; on a `status` event it's read with `terminal.get`, so it is the core's clock and the same after a resubscribe (the phone's only when that read fails or the word already moved on) |
| `turn` (up each time it leaves working) | `completionSeq` | which finish was seen |
| `foreground.cwd`, else `cwd` | Agent `cwd` | |

What follows on the screens:

- **Agents and Needs you**: hc's agents appear with the classic ones (`HomeAgent` reads `SessionSnapshot`). A blocked one can be answered with its keys (`terminal.keys`: `y`, `enter`, `esc`). `terminal.send` refuses a blocked program (kind `blocked`) unless forced.
- **Notifications**: the app derives them from the status changes it follows (`Notices.between` on two snapshots), so herdr-core's snapshots raise the same notices for working → done and → blocked; the events stream keeps them live.
- **Terminals**: `HcTerminalStream` and classic herdr's `TerminalStream` are both a `LiveTerminal` (emulator, revision, status, send, resize, scroll, close), so the Terminal screen takes either. It is fed by `terminal.attach`; hc sends the program's raw bytes, so the app's own emulator draws them. Attaching takes the terminal's size at once (hc: the last active viewer sets it), as classic herdr's takeover does; a watch-only attach (`observe`) never types or resizes the person's window. When the desktop window takes the size back (someone typed there), hc's `size` event says so; HA-6 passes it to `programResized` so the emulator follows.
- **Chats**: hc reports no transcript, so the app finds it from the agent's process (`foreground.pid`), as Shepherdr 3.1's chat does: Claude Code names its session in `~/.claude/sessions/<pid>.json`, codex keeps its `rollout-*.jsonl` open (`/proc/<pid>/fd`); the process's children are tried too. Several agents share a `cwd` (an Assistant and its tasks' workers), so the folder alone can't tell them apart. Where none is found (another agent, a Claude Code that hasn't written its first turn, a terminal on a machine hc added), the chat is its screen (`terminal.read`), as a classic agent without a session's is.

## No match

- **Layouts**: hc has no splits, zoom or focus; each tab's panes are a list. The desktop app keeps its layout to itself.
- **Workspace metadata and worktrees**: hc has no `workspace.report_metadata` tokens (branch, PR) and no `worktree.*`.
- **Plugins, integrations, agent manifests, config reload**: herdr's; hc has templates (`templates.list`) instead.
- **SSH sessions**: the one `hc connect` holds an SSH session for the connection's life, beside classic herdr's (OpenSSH allows 10 by default).
- **Ordering against classic agents**: `stateChangeSeq` is an epoch time here and a counter in classic herdr; sorting one machine's agents works, mixing both needs a common key (HA-6).
- **Creating workspaces and tabs**: spaces and tabs are the desktop app's (`herdr-app do`, a GUI control socket); hc can start a terminal (`terminal.run`) and label it into a space.
- **Agent sessions** (`agent_session`): none; the app sets one of kind `pid` (`HcMapping.sessionOf`), see Chats.
- **herdr's "seen"** (done becomes idle once looked at): hc can't tell; `turn` is the closest.

## On the screens

- **One view**: `HostState.view` is classic herdr's snapshot and herdr-core's together (`Sessions.merge`, classic first, herdr-core's spaces numbered after). The Agents list, Needs you, notices, Live Updates, search, the chats, the machine list and the Terminal screen read it; `HostState.snapshot` stays classic herdr's alone, for what only classic herdr has (layouts, workspace metadata, the brief). When classic herdr stops on a machine running both, the machine stays online for herdr-core and shows only what is live; classic herdr's last snapshot is kept aside, and its agents' pins, and the mutes and watches still to move onto their spaces, wait for it (`HostState.agentsKnown`).
- **Keys and words**: `HostSession.awaitAgent(paneId)` gives an `AgentPort`: herdr-core's (`HcAgentPort`) for a pane id with `hc:`, else classic herdr's. `AgentInput` (the chat, the Needs you card's Yes and No, a notification's buttons, Stop on a Live Update) speaks only to it, so an answer is read off the screen again and pressed the same way on either.
- **Chat**: Claude Code's and codex's transcripts, found from the agent's process (`AgentSessionRef` kind `pid`, which `TranscriptFollower.FIND` looks up on the machine), folded as a classic agent's are; else the agent's screen (`terminal.read`). A question on it gets its card and buttons as a classic agent's does. Classic herdr's own actions (rename, focus, why this state, activity) are left out for herdr-core's agents.
- **Terminal**: `HcTerminalStream`; the desktop window taking the size back (`size` event, `HerdrCoreState.sizes`) resizes the phone's emulator. hc has no scroll request, so the phone keeps the history, as a classic terminal does: the emulator keeps the 2000 lines that scroll off its main screen, and on attaching `terminal.read`'s history (asked just before the attach, 1000 lines, as text without colours) goes above the first paint where its tail meets it (`TerminalHistory.above`). Swiping scrolls through it, typing or **Back to the screen** returns; Find searches it on the phone (`TerminalFind`), marking the match and scrolling to it. Selection by herdr and links are classic herdr's; selected text is read off the phone's own screen (or the history scrolled to) instead.
- **Machine screen**: classic herdr's workspaces, then a **Desktop app** section with herdr-core's spaces, tabs and terminals (no actions on them). The machine list shows herdr-core's version and its agents in the counts.
- **Notifications**: herdr-core's snapshots raise the session's notices as classic herdr's do (none on the first look). While the app is closed, herdr-push (version 9) reads the default core's agents on its socket (plain JSON-RPC, `terminal.list` and `terminal.read`; connecting never starts a core) and pushes them with the classic ones; the app's own look reads them as far as herdr-core was found. herdr-push still reads the default session alone: other sessions' agents raise notices while the app runs, not yet while it is closed.
- **Which machine**: herdr-core belongs to the host, not a herdr session, so the app follows it from the machine entry for classic herdr's default session only: two machines in the app for two sessions of one host show its agents once.
- **Several herdr-core sessions**: `HostSession` follows each session that runs (one `hc connect` each, at most three besides the default one: each holds an SSH channel). A session with no live terminal (a preview's) is let go again after its first look and looked at again a minute later. Ids keep the session apart: the default session's stay `hc:t7`, another's are `hc:@<session>:t7` (`HcMapping.scope`, `HcMapping.session`), so the same `t7` in two sessions is two panes, and each terminal is in exactly one. `HostState.herdrCore` is every session's state as one (`HerdrCoreState.merge`: the default session's spaces first; `sessions` names them), and `awaitHerdrCore(paneId = …)`/`awaitAgent` reach the pane's own session. The machine screen's section is then called **herdr-core** and names the sessions; the machine list adds them after the version. A machine where classic herdr is missing is online while any session's core runs.
- **Shepherdr's agents**: Shepherdr 3 labels the agents it starts (`herdr.role`, `herdr.coordinator.space` on a space's Assistant; `herdr.task` (`<list>#<n>`) and `herdr.task.space` on a task's worker, which herdr-task names `<ref>-<title>`). The app calls them by their task (`HERD-8`, `HERD-8 reviewer`) or as `<space> Assistant`, and keeps the task and space on the agent (`AgentInfo.shepherdrTask`, `shepherdrSpace`; `HcMapping.shepherdrTask` takes the ref's letters from the worker's name only when its number is the label's). A worker sits in its Assistant's space and tab. On a machine whose board is Shepherdr, opening one from the Agents list, Needs you, a notice or notification, search or the brief opens its task's chat or its space's Assistant, where its cards are (`Panes.openAgent`); the machine screen still opens its screen and terminal.
- **Order**: classic herdr's `stateChangeSeq` is a counter, herdr-core's the time in ms, so on the Agents list a herdr-core agent sorts before classic ones of the same state.
